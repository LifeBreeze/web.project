45초

    원본은 이렇게 동작합니다

    서버 (EscapeServer)

    TcpListener로 최대 4명의 접속을 받고, 모두 답을 제출하면 다음 라운드를 알립니다. 하트가 0이 된 플레이어는 탈락 처리합니다.

    클라이언트 (EscapeClient)

    접속 대기 화면, 게임 화면, 결과 화면 3개의 폼으로 나뉩니다. 수신은 별도 스레드에서 하고 화면 갱신은 Invoke로 넘깁니다.

    간단한 통신 규칙

    START, SUBMIT, HEART|번호|개수처럼 줄바꿈으로 끝나는 문자열 명령을 주고받습니다. 끊겨 들어온 조각은 모아 두었다가 한 줄이 완성되면 처리합니다.

    다른 플레이어 답 보기

    누가 어떤 답을 냈는지 말풍선으로 모두의 화면에 띄우고, 하트 상태도 실시간으로 맞춥니다.

    45초 타이머

    라운드마다 45초를 세고, 시간이 다 되면 오답처럼 하트를 하나 잃습니다.

    직접 만든 그림

    시작 화면, 플레이어 4명, 파라오, 하트, 결과 화면을 이집트 유적 분위기에 맞춰 준비해 넣었습니다.

    디버그 해결 경험

    명령어가 잘려서 도착함

    문제
    여러 플레이어가 동시에 답을 내면 명령이 중간에 끊기거나 두 개가 붙어서 들어와 처리에 실패했습니다.
    원인
    TCP는 메시지 단위가 아니라 바이트 흐름이라서, 한 번 읽을 때 명령이 딱 하나씩 오지 않습니다.
    해결
    받은 문자열을 remain에 이어 붙이고 줄바꿈(\n)으로 나눈 뒤, 마지막 미완성 조각은 다음 수신 때까지 남겨 두었습니다.

    수신 중 화면이 멈추거나 오류가 남

    문제
    서버에서 메시지를 기다리는 동안 창이 멈추고, 받은 뒤 화면을 바꾸면 크로스 스레드 오류가 났습니다.
    원인
    수신 대기를 UI 스레드에서 했고, 다른 스레드에서 폼 컨트롤을 직접 건드렸습니다.
    해결
    수신은 별도 백그라운드 스레드(IsBackground = true)로 돌리고, 화면 변경은 Invoke로 UI 스레드에 넘겼습니다.

    답에 특수 문자를 넣으면 통신이 깨짐

    문제
    답에 |나 줄바꿈을 넣으면 다른 플레이어 화면에 이상한 값이 뜨거나 명령이 무시됐습니다.
    원인
    |와 줄바꿈을 명령 구분 기호로 쓰고 있어서 답 안의 같은 문자가 명령을 쪼갰습니다.
    해결
    보내기 전에 줄바꿈은 공백으로, |는 /로 바꿔 데이터를 정리했습니다.

    탈락한 사람 때문에 다음 라운드로 안 넘어감

    문제
    한 명이 탈락하면 나머지가 다 답을 내도 다음 문제가 나오지 않았습니다.
    원인
    서버가 전체 인원 수만큼 제출이 와야 넘어가도록 세고 있었습니다.
    해결
    살아 있는 인원(GetAlivePlayerCount())만 세고, 탈락한 플레이어의 제출은 무시하도록 바꿨습니다.

    배운 점과 성취

    핵심으로 배운 것

    • TCP 소켓으로 서버와 클라이언트가 문자열 명령을 주고받는 통신 규칙(프로토콜) 설계
    • 멀티 스레드 환경에서 UI를 안전하게 바꾸는 법(Invoke)
    • 여러 폼(대기, 게임, 결과)으로 화면을 나누고 데이터를 넘기는 방법
    • 팀원과 기획, 그림, 코드를 나눠 하나의 게임으로 합치는 과정

    성취

    • 최대 4명이 실시간으로 함께 푸는 온라인 게임을 처음으로 완성했습니다.
    • 하트, 타이머, 다른 사람의 답 말풍선까지 모든 플레이어 화면을 맞춰 보여 줍니다.
    • 2학년 1학기 기말고사 과제로 제출했고, 이 사이트에서 원본 문제와 정답 판정 그대로 체험할 수 있습니다.
